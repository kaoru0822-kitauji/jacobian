# v0.1 specification: generic verification kernel

- Status: Draft, normative implementation target
- Theme: Establish a domain-independent verification boundary

## 1. Scope

v0.1 defines a reusable kernel for bounded, executable mathematical problems.
The kernel understands:

```text
artifact
claim
candidate
predicate
objective
witness
certificate
reduction
budget
provenance
```

Mathematical meaning is supplied by versioned plugins. The core has no built-in
knowledge of graphs, flows, matrices, groups, polytopes, or proof tactics.

v0.1 is validated by at least two structurally different reference plugins.
Their domain schemas and checkers are conformance fixtures, not public-kernel
types.

## 2. Required tools

The authoritative summary is [Tool surface](../tools.md).

### 2.1 `artifact.put`

Store an immutable object using a versioned schema and canonicalizer.

Input:

```json
{
  "schema_uri": "artifact://sha256/...",
  "semantics_uri": "artifact://sha256/...",
  "payload": {},
  "parents": [],
  "summary": "bounded candidate"
}
```

Output:

```json
{
  "artifact_uri": "artifact://sha256/...",
  "object_digest": "sha256:...",
  "manifest_digest": "sha256:...",
  "canonicalizer_digest": "sha256:..."
}
```

Requirements:

- The server validates and canonicalizes the payload.
- Clients cannot choose the returned digest.
- Exact artifacts contain no JSON floating-point numbers.
- Canonical rationals are reduced, have a positive denominator, and encode zero
  as `{"num": "0", "den": "1"}`.
- Object identity binds schema, semantics, and canonicalizer versions.
- Blob writes are atomic.

### 2.2 `claim.validate`

Check that a formal problem specification is well-formed.

Input:

```json
{
  "claim_uri": "artifact://sha256/...",
  "plugin_id": "artifact://sha256/..."
}
```

The response reports:

- schema and reference validity;
- declared domains and quantifiers;
- exact-value and bound validity;
- the resolved semantics digest;
- required and available plugin capabilities;
- errors and warnings.

This tool does not establish:

- correspondence between the formal and informal statements;
- truth or falsehood of the claim;
- completeness of an evaluator or semantic implementation.

### 2.3 `evaluate.batch`

Evaluate several candidates with a named problem plugin.

Input:

```json
{
  "claim_uri": "artifact://sha256/...",
  "candidate_uris": ["artifact://sha256/..."],
  "evaluator_id": "artifact://sha256/...",
  "profile": "FAST",
  "seed": 42,
  "budget": {
    "wall_seconds": 60,
    "memory_mb": 4096,
    "parallelism": 8
  }
}
```

Required profiles:

```text
FAST
EXACT_CANDIDATE
```

The plugin may define additional profiles through a versioned schema.

The result includes:

- well-formedness;
- objective vector;
- proposed witnesses;
- arithmetic and coverage actually used;
- features and failure classifications;
- evidence and trace URIs;
- evaluator, environment, and seed provenance.

All evaluations return `verification = UNVERIFIED`. Exact arithmetic and
exhaustive evaluation are useful evidence but do not authorize the evaluator
to certify itself.

### 2.4 `witness.find`

Attack a candidate by searching for a counter-witness or rescuing witness.

Input:

```json
{
  "claim_uri": "artifact://sha256/...",
  "candidate_uri": "artifact://sha256/...",
  "oracle_id": "artifact://sha256/...",
  "witness_role": "DEFEATS_CANDIDATE",
  "budget": {
    "wall_seconds": 300
  }
}
```

Search outcomes:

```text
FOUND
NONE_CERTIFIED
SEARCH_EXHAUSTED
NOT_FOUND_WITHIN_SCOPE
UNKNOWN
```

`FOUND` returns a proposed witness URI. `SEARCH_EXHAUSTED` may return a proposed
nonexistence or completeness certificate. Neither becomes verified until its
authorized checker accepts it. `NONE_CERTIFIED` is permitted only when the
response references a successful `certificate.verify` record for that exact
claim, semantics, candidate, scope, and certificate.

### 2.5 `witness.verify`

Independently replay a concrete witness.

Input:

```json
{
  "claim_uri": "artifact://sha256/...",
  "candidate_uri": "artifact://sha256/...",
  "witness_uri": "artifact://sha256/...",
  "checker_id": "checker://sha256/..."
}
```

The checker verifies:

- claim, semantics, candidate, and witness digest bindings;
- candidate and witness well-formedness;
- witness membership in the quantified domain;
- the exact predicate defining its claimed logical effect.

A direct counter-witness does not require exhaustive coverage. The checker may
share stable wire schemas with the search side but must not import the
evaluator, witness oracle, mutators, or solver integration.

### 2.6 `shrink.run`

Reduce a candidate or witness while preserving a checked predicate.

Input:

```json
{
  "target_kind": "candidate",
  "target_uri": "artifact://sha256/...",
  "claim_uri": "artifact://sha256/...",
  "preservation_checker_id": "checker://sha256/...",
  "reducers": ["delete_element", "reduce_integer"],
  "objectives": ["elements", "max_integer"],
  "budget": {
    "evaluations": 10000
  }
}
```

Supported target kinds:

```text
candidate
witness
```

Reducers are plugin capabilities. Every accepted reduction is replayed through
the authorized preservation checker.

Minimality is reported as:

```text
NONE
LOCAL
ONE_STEP
BOUNDED_GLOBAL
PROVED_GLOBAL
```

`PROVED_GLOBAL` requires an independently checked completeness certificate.

### 2.7 `certificate.verify`

Verify a self-describing certificate with an operator-authorized checker.

Input:

```json
{
  "certificate_uri": "artifact://sha256/..."
}
```

Certificates bind:

```json
{
  "certificate_type": "finite_enumeration",
  "format_version": "1",
  "claim_digest": "sha256:...",
  "semantics_digest": "sha256:...",
  "candidate_digest": "sha256:...",
  "encoding_digest": "sha256:...",
  "payload_digest": "sha256:..."
}
```

`candidate_digest` or `encoding_digest` may be explicitly absent when the
certificate format does not use one.

The certificate format and trust registry determine the checker. Callers and
plugins cannot supply arbitrary executable checker code.

Registered v0.1 certificate formats must include at least:

- direct finite witness;
- complete finite enumeration.

The registry is designed to add SAT/PB proofs, rational duals, Farkas
certificates, interval proofs, and proof-assistant terms without changing the
generic result envelope.

## 3. Optional plugin tools

A plugin may expose typed domain tools, such as:

```text
family.materialize
structure.canonicalize
polytope.separate
```

These are discoverable capabilities rather than mandatory v0.1 tools. Their
outputs remain unverified unless replayed through an authorized checker.

## 4. Common result envelope

Every mathematical tool uses the model defined in
[Architecture](../architecture.md#common-result-model).

Only an operator-authorized checker invocation may originate a `VERIFIED`
record. The public verification entry points are `witness.verify` and
`certificate.verify`. `shrink.run` may surface a verified final artifact only
when every accepted step used an authorized preservation checker and the final
artifact has a fresh verification record.

## 5. Plugin manifest and capabilities

Each installed plugin has an immutable manifest:

```json
{
  "plugin_schema_version": "1",
  "plugin_id": "artifact://sha256/...",
  "domain_id": "bounded-matrix.example",
  "semantics_uri": "artifact://sha256/...",
  "candidate_schema_uri": "artifact://sha256/...",
  "witness_schema_uris": ["artifact://sha256/..."],
  "capabilities": {
    "Evaluator": "artifact://sha256/...",
    "WitnessOracle": "artifact://sha256/...",
    "Reducer": "artifact://sha256/..."
  }
}
```

Trusted checkers are not registered through this manifest. The
operator-controlled checker registry separately associates authorized checkers
with compatible claim, semantics, witness, and certificate versions.

## 6. Trust registry

The registry binds:

```text
checker identifier and executable digest
supported claim schema versions
supported semantics versions
supported witness or certificate formats
authorization and revocation state
```

Registration and revocation events are auditable. A revoked checker does not
invalidate its historical record automatically, but policy determines whether
new verification records may rely on it.

## 7. Storage

v0.1 uses:

- a digest-keyed local filesystem for blobs;
- SQLite in WAL mode for manifests, runs, registry metadata, and indexes;
- immutable completed run records;
- temporary staging paths followed by atomic rename;
- configurable artifact, trace, and retention limits.

Cache keys bind claim, semantics, candidate, evaluator or checker, profile,
environment, and any scope-defining parameters.

## 8. Reference-plugin requirements

At least two structurally different plugins must pass the conformance suite
before the v0.1 capability API is considered stable:

1. A bounded graph/routing plugin that stresses semantic closure and hidden
   witnesses.
2. A bounded matrix or other non-routing plugin with different candidates and
   witnesses.

See [Reference benchmarks](../benchmarks.md). Domain-specific facts and schemas
belong to those benchmark packages, not this specification.

## 9. Acceptance and adversarial tests

The release must:

1. Store and replay candidates from both reference plugins.
2. Verify direct counter-witnesses using independent checker code.
3. Verify complete finite enumeration certificates.
4. Reject a witness outside its declared domain.
5. Reject a certificate bound to another claim, semantics, or candidate.
6. Reject malformed and noncanonical exact values.
7. Keep identical bytes under different schemas or semantics distinct.
8. Treat timeout and execution error as non-conclusions.
9. Ignore a plugin's attempt to self-register a checker.
10. Recheck every accepted shrink step.
11. Refuse exhaustive conclusions when declared limits are reached.
12. Reproduce verified results from artifacts in a clean process.

## 10. Non-goals

- Automatic conjecture discovery
- Representation transformation
- Generic structure enumeration
- Arbitrary executable problem uploads
- Generic solver access
- Distributed execution
- Natural-language formalization
- Proof-assistant search
