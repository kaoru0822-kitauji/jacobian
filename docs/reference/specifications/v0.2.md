# v0.2 specification: bounded discovery

[Documentation home](../../index.md)

- Status: Implemented alpha; normative for `0.2.0a0`
- Theme: Search bounded spaces and verify representation changes

The repository also contains provisional M3/M4 implementations. Their
milestone documents are design and test targets, not additions to this v0.2
wire or artifact contract.

## 1. Scope

v0.2 is the only current Jacobian release contract. It defines a reusable
kernel for bounded, executable mathematical problems. The kernel understands:

```text
artifact
claim
candidate
predicate
objective
witness
certificate
reduction
budget
provenance
```

Mathematical meaning is supplied by versioned plugins. The core has no
built-in knowledge of graphs, flows, matrices, groups, polytopes, or proof
tactics.

## 2. Verification tools

### `artifact.put`

Store an immutable object using a registered schema and canonicalizer. The
server validates and canonicalizes the payload; callers cannot select its
digest. Exact artifacts contain no JSON floating-point values. Canonical
rationals are reduced, have a positive denominator, and encode zero as
`{"num": "0", "den": "1"}`. Object identity binds the schema, semantics, and
canonicalizer versions.

### `claim.validate`

Check that a formal claim is well-formed, including its schema references,
domains, quantifiers, exact values, bounds, resolved semantics, and required
plugin capabilities. Validation does not prove that the formal claim matches
an informal conjecture or that its evaluator is complete.

### `evaluate.batch`

Evaluate multiple candidates using a named problem plugin. Each result reports
its objective vector, proposed witnesses, actual arithmetic and coverage,
features, evidence handles, and evaluator provenance. Evaluation always
returns `verification = UNVERIFIED`, even when it uses exact arithmetic or
reports exhaustive coverage.

The required evaluation profiles are `FAST` and `EXACT_CANDIDATE`. The current
implementation executes a batch sequentially and applies its wall-clock limit
to the whole batch.

### `witness.find`

Attack a candidate by searching for a counter-witness or rescuing witness.
Valid outcomes are `FOUND`, `NONE_CERTIFIED`, `SEARCH_EXHAUSTED`,
`NOT_FOUND_WITHIN_SCOPE`, and `UNKNOWN`. A found witness remains proposed until
independent replay. `NONE_CERTIFIED` is valid only when it references a
successful verification record bound to the exact claim, semantics,
candidate, and scope.

### `witness.verify`

Independently replay a concrete witness. The authorized checker verifies all
bindings, the candidate and witness domains, and the exact predicate defining
the witness's logical effect. It must not import the evaluator, witness oracle,
mutators, or solver integration that produced the witness.

### `shrink.run`

Reduce a candidate or witness while preserving a checked predicate. Each
accepted step must strictly improve the declared objective vector and pass an
authorized preservation checker. The result reports `NONE` or `LOCAL`
minimality. Stronger claims require independently checked completeness
evidence and are not emitted by `0.2.0a0`.

### `certificate.verify`

Verify a self-describing certificate using an operator-authorized checker.
Certificates bind the claim, semantics, candidate when applicable, scope,
encoding when applicable, certificate format, and payload digest. Plugins and
callers cannot supply arbitrary checker code.

The initial registered evidence formats include direct finite witnesses,
complete finite-enumeration certificates, verified transformations, exact
finite convex combinations, and exact finite separators.

## 3. Common verification and storage contract

Execution status, input validity, mathematical conclusion, assurance, evidence
type, and verification state are orthogonal. `TIMEOUT`, `CANCELLED`, `ERROR`,
incomplete coverage, and failure to find a witness never imply a mathematical
conclusion.

Only `witness.verify`, `transform.verify`, or `certificate.verify` may originate
a `VERIFIED` record. Search and solver output remain evidence.

Plugins have immutable manifests describing their schemas, semantics, and
untrusted capabilities. Trusted checkers are authorized separately in an
operator-controlled registry that binds checker bytes, compatible schemas and
semantics, evidence formats, and revocation state.

The local implementation uses a digest-keyed filesystem for blobs, SQLite in
WAL mode for metadata and policy, atomic blob commits, immutable verification
records, and configured artifact-size limits.

## 4. Bounded-discovery tools

### `search.enumerate`

Launch an exhaustive bounded search using a plugin-provided
`CandidateEnumerator`.

```json
{
  "claim_uri": "artifact://sha256/...",
  "plugin_id": "artifact://sha256/...",
  "bounds": {
    "vertices": 8
  },
  "quotient_by_isomorphism": true,
  "profile": "EXACT_CANDIDATE",
  "seed": 0,
  "budget": {
    "candidates_max": 1000000,
    "wall_seconds": 3600,
    "page_size": 128
  }
}
```

It returns an `experiment://...` handle immediately. Progress, archive
snapshots, scope, and accounting data are available as resources.

The Python and MCP interfaces use this asynchronous behavior. The local CLI
waits for completion and prints the terminal snapshot because it has no
resident worker process.

The alpha experiment store has one live process owner. Do not open the same
state directory from another Jacobian process while an experiment is running;
startup recovery treats nonterminal rows as interrupted work. Multi-process
leases remain outside v0.2. The provisional M3 strategy runtime adds
checkpoint-based restart recovery, but still requires one active coordinator
per state directory.

Enumeration completeness is not inferred from the absence of candidates. A
negative mathematical result requires a checked enumeration certificate.

### `structure.canonicalize`

Compute a canonical representation, automorphism information, and orbits for a
supported finite structure.

The output is suitable for search deduplication. If canonicalization affects an
exhaustiveness claim, its correctness must be independently justified or
checked.

### `transform.apply`

Propose or compute a new representation and a proof obligation.

Supported relation labels:

```text
EQUIVALENT
OVER_APPROXIMATION
UNDER_APPROXIMATION
HEURISTIC
```

The transformer remains untrusted.

### `transform.verify`

Verify a transformation obligation and bind:

```text
source object and semantics
target object and semantics
claimed relation
obligation payload
checker digest
```

Only this tool may mark a transformation verified.

### `polytope.separate`

Perform typed exact operations over finite rational generator sets:

- convex-hull membership;
- coordinate projection;
- strict linear separation.

Outputs remain unverified until an exact convex-combination witness or
separator certificate is accepted by `witness.verify` or
`certificate.verify`.

The initial backend is deliberately finite V-representation only. H-to-V and
V-to-H conversion, implicit polytopes, redundancy removal, and general facet
or incidence enumeration require an optional exact polyhedral backend and are
not part of the `0.2.0a0` contract.

### `experiment.cancel`

Cancel a running persistent experiment. Completed artifacts remain immutable.

## 5. Domain capabilities and checker roles

Plugins may optionally expose these untrusted capabilities:

```text
CandidateEnumerator
Canonicalizer
Transformer
```

There is no separate public `structure.enumerate`; `search.enumerate`
orchestrates a domain enumerator.

`TransformationChecker` and `EnumerationCertificateChecker` are authorized
checker-registry roles, not plugin capabilities. This prevents a transformer or
enumerator from registering the code that certifies its own output.

`PolytopeBackend` is an internal typed backend interface. It is not a universal
plugin capability or public solver tool in `0.2.0a0`.

## 6. Backends

Initial backends:

- a transparent exhaustive reference canonicalizer for graphs of at most nine
  vertices;
- Z3 exact rational constraints for finite convex membership and separator
  generation;
- independent Python `Fraction` replay checkers.

nauty/gtools and `cdd.gmp` remain recommended optional production backends.
They are not default dependencies because the available Python bindings add
native-system or incompatible licensing constraints.

Backend status is evidence. The public conclusion is determined by Jacobian
checkers.

## 7. Cross-domain requirement

Exercise bounded discovery in both reference domains. The non-graph
plugin must confirm that enumeration and transformation APIs do not assume:

- every candidate has a useful canonical graph label;
- mutation is mandatory;
- semantic closure is always path enumeration;
- witnesses have the same type as candidates.

## 8. Release gate

v0.2 is complete only when:

1. Candidates from two structurally different plugins are stored, evaluated,
   attacked, shrunk, and independently verified.
2. Direct witnesses and finite certificates reject domain, binding, payload,
   checker-authorization, and revocation attacks.
3. Timeouts, limits, cancellation, errors, and incomplete coverage remain
   non-conclusions.
4. A bounded candidate class is enumerated with auditable scope.
5. Search deduplication rejects isomorphic duplicates.
6. A representation change is independently verified.
7. An exact rational separator is generated and checked.
8. An interrupted experiment can be inspected and cancelled without
   corrupting completed artifacts.

The detailed behavioral gate is
[v0.2 conformance](../conformance-v0.2.md).

## 9. Non-goals

- Evolutionary or learned search
- Distributed workers
- Concurrent process ownership of one live experiment store
- Model-uploaded code
- Automatic motif recognition
- General theorem proving
