# v0.3 specification: scalable search

- Status: Provisional
- Theme: Place large search loops inside the engine

## 1. Entry gate

Two domains must have validated the v0.2 enumeration, transformation, and
verification boundaries.

## 2. New tools

### `search.evolve`

Run evolutionary or program search with:

- multiple proposers;
- Pareto objectives;
- island populations;
- lineage;
- novelty over canonical, score, and failure signatures;
- scheduled exact-candidate evaluation;
- verification of promoted results.

Program candidates are permitted through operator-installed local plugins.
They remain mathematically untrusted even though the operator trusts them to
execute on the host.

### `search.cegis`

Run a counterexample-guided loop:

```text
propose candidate
    → find defeating witness
    → verify witness
    → refine candidate constraints
    → repeat
```

A search exhaustion result is not a proof unless its associated certificate is
checked.

### `search.tree`

Run beam, best-first, Monte Carlo tree, or related state-space search. This
supports construction search and later proof-state search without forcing them
into the evolutionary abstraction.

### `family.compile`

Compile a semantic family into a non-explicit representation:

```text
BDD
ZDD
finite automaton
dynamic-programming DAG
separation or pricing oracle
```

The representation records its scope and any unverified completeness claim.

### `experiment.pause` and `experiment.resume`

Checkpoint and resume supported searches. Checkpoints bind the search policy,
plugin, artifact, environment, and random-state digests.

## 3. Search archives

Every experiment stores:

```text
candidate
parents
proposer and mutation description
objective vector
evaluation assurance
failure witness
verified failure classification
feature vector
solver and environment versions
timestamps and resource usage
```

Archives are multi-objective. A single scalar score is optional and cannot
replace hard validity constraints or assurance labels.

## 4. Execution

Scale in this order:

1. Sequential reference implementation
2. Spawned local worker processes
3. Persistent local experiment queue
4. Distributed workers only after measured need

Local workers use explicit wall-clock and output limits, fixed seeds where the
backend supports them, and recorded environment identities. These are
operational and reproducibility controls, not a security sandbox. Jacobian does
not accept arbitrary executable uploads; operators install plugins and checkers
they consider safe to run locally.

## 5. Exit gate

v0.3 is complete when:

- a long search can pause, resume, and reproduce its archive lineage;
- counter-witnesses influence subsequent proposals;
- promoted candidates cross the existing checker boundary;
- worker timeout, output-limit, and resource-exhaustion tests fail safely;
- distributed execution, if present, cannot forge checker authorization.
